# 0003. 봇 차단·로그인·robots.txt 거부는 뚫지 않고 돌아간다

| 상태 | 날짜 |
|---|---|
| **채택** | 2026-09-11 |

## 현상

1주차 실측에서 후보 소스 10곳 중 5곳이 403 이었고(진에어·에어부산·에어서울·뽐뿌 HTML·플레이윙즈), 브라우저
컨테이너로도 뚫리지 않았다. 잡코리아는 robots.txt 로 검색 경로(`/Search/?stext=`)를 명시 거부하고 있었는데,
그걸 모르고 감시를 등록한 상태였다. Cloudflare 우회 도구(FlareSolverr 류)나 로그인 자동화로 뚫을 수는 있다.

## 결정

뚫지 않는다. 소스는 다음 순서로 고르고, 다 안 되면 "이 소스는 안 된다"를 사용자에게 바로 알린다.

1. 피드·공개 API·사이트 자체 알림
2. 공개 웹 페이지 (robots 허용, 필요시 브라우저 렌더링)
3. 이메일 — 로그인이 필요한 서비스는 대개 자기가 알림 메일을 보낸다. 그것을 소스로 받는다
4. 폰 알림 (안드로이드)
5. LLM 검색 (뉴스 종류 전용 마지막 폴백)

`test_parse` 가 등록 전에 robots.txt 를 읽어 거부면 `blocked` 로 돌린다. 정책을 문서가 아니라 코드에 둔다.

## 이유

- 사이트의 명시적 거부를 뚫는 것은 정책상 문제고, 대책이 바뀔 때마다 깨지며, 포트폴리오에 "차단 우회"가 남는다.
- 로그인 자동화는 세션 만료·2단계 인증·계정 제재 위험이 커서 개인 실사용 도구로 불안정하다.
- 정보는 한 곳에만 있지 않다. 항공사 페이지가 막혀도 Google 특가·커뮤니티 피드로 같은 것을 받았고,
  잡코리아가 막혀도 사람인이 허용이었다.

## 트레이드오프

- 어떤 주제는 소스가 아예 없을 수 있다. 그때는 이메일·LLM 검색으로 내려가거나 포기한다. 포기를 빨리 알리는 것이 자동화의 몫.
- robots.txt 는 의사 표시지 법적 구속은 아니라서, 허용인데 403 인 경우와 거부인데 200 인 경우가 다 있다. 둘 다 `blocked` 로 본다.
