# 프로젝트 플랜 — 말 한 줄이 감시 한 건이 되는 구조 (v1.1)

> 작성일: 2026-08-26 · **v1.1 개정 2026-09-11** (레시피·소스 5갈래·알림 4종류·접수 양식·실행 위치) · 레포 이관 2026-08-29
> v0 설계(게임뉴스 특화)는 [`docs/design-v0.md`](./design-v0.md) 참고

---

## 1. 목표

사용자가 자연어로 "○○ 알람 받고 싶어"라고 주문하면, 어떤 서비스든 감시를 등록하고
**ntfy 푸시로 알림을 받는** 개인 알람 시스템.

- 개인 실사용 도구이자 취업 포트폴리오 프로젝트
- 특정 도메인(게임/영화/채용)에 국한하지 않는 **범용 구조**
- 실시간 티켓팅 X — "그날 안에 알면 되는" 수준의 알림

## 2. v0 → v1: 무엇이, 왜 바뀌었나

| 항목 | v0 (2025, 설계만) | v1 (현재) | 변경 이유 |
|---|---|---|---|
| 범위 | 게임뉴스 특화 | 도메인 무관 범용 | 발레 공연이든 뭐든 되게 |
| 크롤러 | 소스별 자체 구현 (BS4/Playwright) | **changedetection.io 엔진** 재사용 | 파서 유지보수·봇 차단은 검증된 엔진에 위임 |
| LLM | Ollama Mistral 7B 로컬, 분류·요약 담당 | **접수·서술만** (판정은 코드) | AITCH 원칙 재사용 |
| 알림 | 카카오톡 (MCP) | **ntfy** (공용 ntfy.sh) | 셀프호스팅 불필요, curl 한 줄 |
| 인터페이스 | 없음 | **자체 MCP 서버** → Claude가 앞단 | 자연어 주문 접수 층을 무료로 획득 |
| 실행 환경 | 개인 PC (RTX 3070) | GitHub Actions cron 우선 | 상시 서버 불필요, 무료 |

핵심 통찰: v0에 이미 "AI Agent가 사이트 분석 → 크롤링 규칙 자동 추출" 아이디어가
있었다. v1은 이를 **"LLM이 설정 초안 생성 → 검증 통과 후 등록"**으로 안전하게 재설계한 것.

## 3. 확정 아키텍처

```
사용자 (자연어 주문)
    │  "발레 공연 알람 받고 싶어"
    ▼
Claude ──── 자체 MCP 서버 ──── changedetection.io (감시 엔진, API 조작)
              │ add_watch                │ 폴링·diff·렌더링
              │ list_watches             ▼
              │ remove_watch          변경 감지
              │ test_parse               │
              │ get_history              ▼
              └───────────────────► ntfy.sh ──► 폰 푸시
                                   (모듈별 토픽 = 구독이 곧 범위 선택)
```

- **감시 엔진**: changedetection.io — 직접 만들지 않고 API로 조작
- **알림**: 공용 ntfy.sh, 토픽명은 추측 어렵게. 토픽 분리(`*-jobs`, `*-movie` 등)
- **내가 만드는 것**: changedetection.io API를 감싸는 **MCP 서버**와 그 앞뒤의 얇은 층 둘 — 접수·검증(레시피·test_parse), 판정·발송(중복·다이제스트·피드백). 판정은 코드, LLM 은 접수와 서술만
- **단일 사용자.** "누군가는 축구팀을 등록할 수 있다"는 레시피의 범용성이지 멀티유저 서비스가 아니다. 인증·요금·사용자 격리는 만들지 않는다
- **실행 환경**: 감시 엔진은 **로컬 PC Docker** ([ADR 0001](./adr/0001-changedetection-로컬-docker.md), 2026-09-11).
  당초의 GitHub Actions cron 은 상시 프로세스를 못 둬서 접었다. 하트비트·자체 워처 같은 무상태 작업만 Actions 에 남긴다
- **폴링 주기**: 채용 30분~1시간 · 뉴스 1시간 · 영화관 취소표 10~15분 · 항공권 특가 12시간·커뮤니티 피드 1시간

### 3층 구조 (모르는 서비스 대응)

1. **만능 폴백** — "이 페이지 이 영역이 바뀌면 알림" (diff 감시, 어떤 URL이든 즉시 작동)
2. **구조화 모듈** — RSS/API/셀렉터 설정 보유, 키워드·조건 필터 가능
3. **LLM 승격** — 주문을 받아 셀렉터 설정 초안 생성 → `test_parse` 검증 통과 시 2층으로 승격, 실패 시 1층 폴백

### 레시피 — 카테고리는 코드가 아니라 데이터 ([ADR 0002](./adr/0002-레시피는-데이터.md))

주제 하나 = `recipes/<name>.yaml` 하나. 무엇을(topic) · 어떤 종류로(kind) · 어디서(sources) · 얼마나(every, mode) · 어디로(topic → ntfy) 를 파일이 들고, 코드는 레시피를 읽어 등록·갱신·삭제하는 한 벌만 둔다. `verified` 가 없으면 등록을 거부한다. 레시피가 정본이라 엔진 데이터가 날아가도 `recipes sync` 로 복구된다. 필드는 `watchog/recipes.py` docstring.

### 알림 4종류 — 주제가 아니라 신호의 모양으로

| kind | 예 | 판정 | 발송 | 상태 |
|---|---|---|---|---|
| `diff` 변화 | "이 페이지 이 영역이 바뀌면" | diff 그대로 | 즉시 | 가능 |
| `item` 새 항목 | 채용 공고, 뉴스, 핫딜 글 | 목록에서 못 본 항목 (seen-set + 중복 묶기) | 즉시 또는 다이제스트 | 가능 |
| `threshold` 조건 | 가격 X 이하, 예매 오픈, 재입고 | 값을 파싱해 비교. 상태가 넘어가는 순간 한 번만 | 즉시, urgent | 4주차 |
| `event` 일정 | 경기 일정, 패치 날짜 | 항목에 날짜. 새 일정 + 직전 리마인더 | 생기면·당일 | 4주차 (캘린더 동기화가 붙는 자리) |

"리버풀 소식 다" 는 레시피 둘(뉴스=item·digest, 일정=event)로 갈라 접수한다.

### 소스 5갈래와 우선순위 ([ADR 0003](./adr/0003-막힌-소스는-뚫지-않는다.md))

1. **피드 · API** — RSS, 공개 JSON, 사이트 자체 알림. 차단 거의 없고 항목 단위
2. **웹 페이지** — robots 허용인 공개 페이지. 필요시 브라우저 렌더링(로컬 Docker 만)
3. **이메일** — 로그인 필요한 서비스의 정답. 사이트가 보내주는 알림 메일을 Gmail 라벨 → IMAP 으로 (미구현)
4. **폰 알림** — 안드로이드 Tasker → ntfy inbox 토픽 → 규칙+LLM 판정 → 통과분만 재발송 (미구현)
5. **LLM 검색** — Gemini grounding. 뉴스 종류 전용 마지막 폴백 (미구현)

뚫지 않는 것: Cloudflare 우회 도구, 로그인 자동화, 로컬 LLM·임베딩(PC 는 게임용, 판정은 코드라 로컬일 이유가 없다 — 전부 Gemini API 무료 티어).

### 접수 양식 — 문장 대신 빈칸 다섯

| 빈칸 | 예 | 비어 있으면 |
|---|---|---|
| 무엇 | 리버풀 · 「듄 3」 용산 IMAX | 필수 |
| 종류 | 뉴스 / 일정 / 조건 / 그냥 변화 | 되묻는다. "소식 다" 는 둘로 갈라 제안 |
| 어디서 | URL 또는 "몰라" | 코드가 피드 자동 발견 → 없으면 LLM 이 후보 2~3개 |
| 얼마나 | 즉시 / 하루 N번 묶어서 | 종류별 기본값 |
| 조건 | "15만원 이하", "예매 오픈" | 조건 종류만 필수 |

이 양식이 그대로 MCP `add_watch` 의 인자다. 등록 전에 `test_parse` 결과(잡힌 항목 N건)를 보여주고 확인받는다.

### 기본 레시피 (2026-09-11)

실제로 받고 싶은 알림 넷은 처음부터 레시피로 둔다.

| 모듈 | 태그 · 토픽 | 무엇을 받나 | 판정 | 비고 |
|---|---|---|---|---|
| 영화관 | `movie` | 세 체인(CGV·롯데시네마·메가박스)의 예매 가능 목록에 새 영화가 뜨면. 특정 영화·IMAX 조건은 나중에 threshold 로 | item → threshold | 롯데는 브라우저로 렌더링됨. **메가박스는 robots 전면 거부(blocked)**, CGV 는 예매 페이지 경로 미확정 |
| 채용 | `jobs` | 검색 조건에 걸린 새 공고 → LLM 이 "내가 원하는 공고인지" 판정 | item (+ LLM 예정) | **사람인** 3 검색어. 잡코리아는 robots 가 검색 경로를 명시 거부해 제외 |
| **항공권** | `flight` | **핫딜** — 특가가 뜨면 알림. 특정 구간 가격 추적은 하지 않는다 | 규칙(키워드) | **2026-09-11 추가.** 소스: Google Flights 특가(서울발 30건, 브라우저 fetcher) + 커뮤니티 핫딜 피드(뽐뿌·루리웹 RSS, 클리앙)를 "항공" 키워드로. 항공사 이벤트 페이지·뽐뿌 게시판 HTML 은 Cloudflare 403 |
| 게임뉴스 | `gamenews` | 패치·이벤트 일정, 커뮤니티 이슈 | 규칙 + LLM | v0 계승. 로드맵 "이후" |

### 중복 처리 세 겹과 다이제스트

| 겹 | 무엇 | 어떻게 | 누가 |
|---|---|---|---|
| 1 | 똑같은 것 (같은 URL·제목 재수집) | 제목 정규화 → 해시 → seen-set (`runner.item_id`) | 코드 |
| 2 | 같은 사건, 다른 기사 | 제목 임베딩(Gemini) → 24~48h 내 코사인 유사도 → 임계값 | 임베딩 + 숫자 |
| 3 | 경계 쌍(0.7~0.85)과 요약 | "같은 사건이야?" + "오늘 ○○ 소식 3건" | LLM |

발송 모드: `instant`(예매 오픈·핫딜·조건) / `digest`(팀 소식·뉴스·채용, N시간마다 한 통). `quiet` 는 시간대와 상태(`gaming`) 둘 다. 이력은 `data/history.sqlite`, 알림마다 「유용 / 무시」 버튼이 ntfy `feedback` 토픽으로 돌아와 임계값·규칙을 고치는 유일한 데이터가 된다.

### 실행 위치 — PC 에 남는 건 브라우저 감시 하나

| 어디서 | 무엇 | 비고 |
|---|---|---|
| GitHub Actions cron | `runner: actions` 레시피 — 피드·requests 페이지·(예정) LLM 검색·임베딩 | `python -m watchog poll`. seen.json 을 레포에 커밋. 시크릿 없으면 dry-run |
| 로컬 Docker | `fetch: browser` 소스 (Google 특가, 영화관) | 게임 프로세스 뜨면 `docker compose pause` (예정) |
| Oracle Free · 태블릿 | 로컬 Docker 몫을 통째로 | PC 를 비우고 싶어지면. ADR 0001 |

### 토큰 예산 — 등록 횟수에 비례, 시간에 비례하지 않음

코드가 먼저 찾는다(피드 자동 발견·카탈로그) → 페이지를 통째로 주지 않는다(반복 구조 블록만 3천 자) → 셀렉터는 LLM 이 쓰지 않고 후보 중 고른다 → 중복은 임베딩 API 제목만 → 다이제스트는 템플릿 기본 → 등급·캐시·레시피별 장부와 일일 상한. 어림: 레시피 등록 수천~1만 토큰, 폴링 0.

## 4. 설계 원칙

1. **판정은 코드, LLM은 접수와 서술만** (AITCH 원칙 재사용)
2. **fail-loud** — watcher 에러 자체를 ntfy로 발송, 조용히 죽지 않게
3. **파서 깨짐 감지** — 결과 0건·구조 변화 시 "확인 필요" 알림
4. **하트비트** — 하루 1회 생존 신호 ("멈춘 걸 모르는 상태" 방지)
5. LLM이 만든 설정은 **검증 통과 후에만 등록**
6. 문제를 전수조사하지 않는다 — 실패를 **범주로 처리**하고, 미지의 문제는 터질 때 범주에 추가

## 7. 포트폴리오 서사 (면접 대비 요약)

- "이미 changedetection.io가 있는데 왜?" → **기존 도구 분석 → 갭 발견(자연어 접수,
  검증 게이트, 승격 구조) → 그 위에 MCP 계층 설계.** 도구 유행 편승이 아니라 설계 얘기
- v0(자체 크롤러 설계) → v1(엔진 재사용 + 얇고 새로운 층)의 진화 자체가
  "같은 문제를 두 번째엔 다르게 푼" 증거
- AITCH의 "LLM 신뢰 경계를 실측으로 정한다" 원칙의 개인 프로젝트 재적용
