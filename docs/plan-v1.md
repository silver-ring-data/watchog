# 프로젝트 플랜 — 모듈식 알람 시스템 (v1)

> 작성일: 2026-08-26 · 상태: 설계 확정, 구현 착수 전 · 레포 이관 2026-08-29 (MyPlayScheduler → watchog)
> v0 설계(게임뉴스 특화)는 [`docs/design-v0.md`](./design-v0.md) 참고

---

## 1. 목표

사용자가 자연어로 "○○ 알람 받고 싶어"라고 주문하면, 어떤 서비스든 감시를 등록하고
**ntfy 푸시로 알림을 받는** 개인 알람 시스템.

- 개인 실사용 도구이자 취업 포트폴리오 프로젝트
- 특정 도메인(게임/영화/채용)에 국한하지 않는 **범용 구조**
- 실시간 티켓팅 X — "그날 안에 알면 되는" 수준의 알림

## 2. v0 → v1: 무엇이, 왜 바뀌었나

| 항목 | v0 (2025, 설계만) | v1 (현재) | 변경 이유 |
|---|---|---|---|
| 범위 | 게임뉴스 특화 | 도메인 무관 범용 | 발레 공연이든 뭐든 되게 |
| 크롤러 | 소스별 자체 구현 (BS4/Playwright) | **changedetection.io 엔진** 재사용 | 파서 유지보수·봇 차단은 검증된 엔진에 위임 |
| LLM | Ollama Mistral 7B 로컬, 분류·요약 담당 | **접수·서술만** (판정은 코드) | AITCH 원칙 재사용 |
| 알림 | 카카오톡 (MCP) | **ntfy** (공용 ntfy.sh) | 셀프호스팅 불필요, curl 한 줄 |
| 인터페이스 | 없음 | **자체 MCP 서버** → Claude가 앞단 | 자연어 주문 접수 층을 무료로 획득 |
| 실행 환경 | 개인 PC (RTX 3070) | GitHub Actions cron 우선 | 상시 서버 불필요, 무료 |

핵심 통찰: v0에 이미 "AI Agent가 사이트 분석 → 크롤링 규칙 자동 추출" 아이디어가
있었다. v1은 이를 **"LLM이 설정 초안 생성 → 검증 통과 후 등록"**으로 안전하게 재설계한 것.

## 3. 확정 아키텍처

```
사용자 (자연어 주문)
    │  "발레 공연 알람 받고 싶어"
    ▼
Claude ──── 자체 MCP 서버 ──── changedetection.io (감시 엔진, API 조작)
              │ add_watch                │ 폴링·diff·렌더링
              │ list_watches             ▼
              │ remove_watch          변경 감지
              │ test_parse               │
              │ get_history              ▼
              └───────────────────► ntfy.sh ──► 폰 푸시
                                   (모듈별 토픽 = 구독이 곧 범위 선택)
```

- **감시 엔진**: changedetection.io — 직접 만들지 않고 API로 조작
- **알림**: 공용 ntfy.sh, 토픽명은 추측 어렵게. 토픽 분리(`*-jobs`, `*-movie` 등)
- **내가 만드는 것**: changedetection.io API를 감싸는 **MCP 서버** (프로젝트의 핵심 기여)
- **실행 환경**: GitHub Actions cron 우선. 데이터센터 IP 차단에 *실제로* 걸린
  모듈만 로컬 기기(태블릿)로 이전
- **폴링 주기**: 채용 30분~1시간 · 뉴스 1시간 · 영화관 취소표 10~15분

### 3층 구조 (모르는 서비스 대응)

1. **만능 폴백** — "이 페이지 이 영역이 바뀌면 알림" (diff 감시, 어떤 URL이든 즉시 작동)
2. **구조화 모듈** — RSS/API/셀렉터 설정 보유, 키워드·조건 필터 가능
3. **LLM 승격** — 주문을 받아 셀렉터 설정 초안 생성 → `test_parse` 검증 통과 시 2층으로 승격, 실패 시 1층 폴백

## 4. 설계 원칙

1. **판정은 코드, LLM은 접수와 서술만** (AITCH 원칙 재사용)
2. **fail-loud** — watcher 에러 자체를 ntfy로 발송, 조용히 죽지 않게
3. **파서 깨짐 감지** — 결과 0건·구조 변화 시 "확인 필요" 알림
4. **하트비트** — 하루 1회 생존 신호 ("멈춘 걸 모르는 상태" 방지)
5. LLM이 만든 설정은 **검증 통과 후에만 등록**
6. 문제를 전수조사하지 않는다 — 실패를 **범주로 처리**하고, 미지의 문제는 터질 때 범주에 추가

## 5. 로드맵 (순서 고정)

| 주차 | 목표 | 완료 기준 |
|---|---|---|
| 1주차 | changedetection.io 가동 + 수동 등록 | 영화관·채용공고 감시 2건 등록, ntfy 폰 수신 확인 |
| 2주차 | MCP 서버 최소 버전 | `add_watch` / `list_watches` / `remove_watch` 3개 도구 작동 |
| 3주차 | 검증 + 자연어 흐름 | `test_parse` 추가, Claude 대화로 감시 등록 성공 |
| 이후 | 모듈 확장 | 게임뉴스(v0 계승), 공연, 기타 |

> ⚠️ 스코프 규칙: 다음 주차로 넘어가기 전에 현재 주차 완료 기준을 먼저 충족할 것.

## 7. 포트폴리오 서사 (면접 대비 요약)

- "이미 changedetection.io가 있는데 왜?" → **기존 도구 분석 → 갭 발견(자연어 접수,
  검증 게이트, 승격 구조) → 그 위에 MCP 계층 설계.** 도구 유행 편승이 아니라 설계 얘기
- v0(자체 크롤러 설계) → v1(엔진 재사용 + 얇고 새로운 층)의 진화 자체가
  "같은 문제를 두 번째엔 다르게 푼" 증거
- AITCH의 "LLM 신뢰 경계를 실측으로 정한다" 원칙의 개인 프로젝트 재적용
